## Что было сломано и уже исправлено

1. **Падал `mobile-iphone` проект целиком (~50 тестов)** — `install-browsers`
   ставил только `chromium`, а мобильный профиль (`iPhone 13`) требует
   WebKit. Поправил скрипт на `playwright install chromium webkit`.
   **У тебя уже стоит старый `node_modules` — команду нужно прогнать
   вручную один раз:** `cd e2e && npx playwright install webkit`.

2. **`Error: statement has been finalized`** при восстановлении бэкапа —
   реальный баг: роут закрывает соединение с БД перед ответом клиенту, а
   `express-session` в этот момент ещё пытается сохранить сессию через то
   же соединение. Раньше это просто печаталось безобразным стектрейсом в
   лог (тест при этом проходил). Теперь хранилище сессий узнаёт этот
   конкретный сценарий и тихо считает его успехом.

3. **Тесты слоя рисования (`annotations.spec.js`) мешали друг другу** —
   рисовали на настоящей карте с 318 островами и не убирали за собой
   пометки. Теперь каждый тест рисования работает в изолированном
   фиктивном проекте.

4. **Гонка в тестах панели настроек** — `renderConfigPanel()` стала
   асинхронной, но тесты считали, что после клика форма уже в DOM.
   Добавлен хелпер `openConfig()`, реально дожидающийся рендера.

5. **Два `strict mode violation` в `users.spec.js`** — `toContainText()` на
   локаторе с несколькими совпадениями. Переключено на `.filter({ hasText })`.

6. **Пинг-тесты падали с `Cannot read properties of undefined`** при пустой
   карте — добавлена защита и фолбэк на «родной» проект.

7. **Зависание `#authOverlay` в `auth.spec.js`/`dragdrop.spec.js`.**
   Причина: `crypto.scryptSync` в `security/passwords.js` синхронный и
   блокирует весь event loop Node на время хэширования пароля. При
   нескольких параллельных воркерах Playwright, логинящихся почти
   одновременно, вызовы scrypt вставали в очередь и блокировали вообще все
   остальные запросы к серверу — на медленной машине посреди длинного
   прогона легко превышало 10-секундный таймаут `loginViaUI`. К rate-limit
   отношения не имело. Переведено на асинхронный `crypto.scrypt`. Проверено:
   12 параллельных логинов — максимум 628мс, без сериализации.
   **Не проверено вживую e2e** — ожидаю, что зависания больше нет, заодно
   должен починиться и необъяснённый `config.spec.js` (цвет акцента,
   переключатель тем — та же гонка из пункта 4).

   (реальная Tab-навигация в браузере) не проверялось.

   (`--void-0`/`--void-1`) — расчётное соотношение контраста ~8:1, выше
   уровня AAA.

## Аудит по ролям (читатель / редактор / админ) — новый раздел, ничего не сделано

### Читатель (гость)

- **Нет URL на конкретный остров — самое критичное.** SPA без роутинга: что
  бы ни было открыто, в адресной строке один и тот же корневой URL.
  Физически нельзя скопировать ссылку на остров или сохранить закладку на
  конкретную статью — только на сайт целиком. Та же причина, по которой
  `sitemap.xml` содержит только главную страницу (см. раздел про
  robots.txt/sitemap выше). Базовая ожидаемая функция любой вики.
- Нет «случайного острова» — стандартная штука для вики-исследования.
- Нет отметки «обновлено N дней назад» на статье — завязано на отсутствующую
  историю правок (см. предложение №3 в «Сделать в первую очередь»).
- Нет способа для незалогиненного гостя предложить правку/сообщить об
  ошибке — либо тишина, либо только полноценная регистрация (которой у
  гостя и так нет — регистрация admin-only).
- Аудит доступности (ARIA/фокус, см. выше) тоже в первую очередь бьёт по
  читателю.

### Редактор

- **Правки уходят в базу мгновенно, без черновика/превью** — опечатался в
  описании острова, все видят сразу же. Отмены нет, кроме ручного
  повторного редактирования (есть toast-отмена в паре мест на удаление, не
  системно).
- **Нет ленты «последние изменения»** — с несколькими редакторами (система
  регистрации уже это поддерживает) никто не видит, что поменяли остальные.
  Слепая зона для координации совместного редактирования.
- **Конфликт одновременного редактирования не обрабатывается** — два
  редактора правят один остров одновременно → молча побеждает тот, кто
  сохранил последним, без предупреждения о перезаписи чужих правок.
- Нет пакетных операций кроме архипелагов (например, массово проставить
  категорию/фракцию нескольким островам разом).

### Админ — самый концентрированный пробел, права буквально бинарные и статичные

Разобрал `routes/auth.js` целиком:
- **Роль нельзя сменить после создания.** Есть только `POST /register`
  (создать нового пользователя) и `DELETE /users/:id` (удалить). Понизить
  админа до редактора или наоборот — только удалить аккаунт и завести
  заново.
- **Всего два уровня прав, без скоупинга.** `editor`/`admin` жёстко зашито
  в `CHECK (role IN ('editor','admin'))`. Нет ничего среднего вроде
  «модератор без доступа к бэкапам» или «редактор только одного проекта»
  (при том что мультипроектность уже есть — права редактора сейчас
  глобальные на все проекты сразу, привязки к конкретному нет).
- **Принудительный сброс пароля — только при создании.** `must_change_password`
  выставляется один раз при регистрации приглашённого; если админ
  подозревает компрометацию чужого пароля позже — заставить сменить при
  следующем входе нельзя, только удалить аккаунт целиком.
- **Нет мягкой блокировки** — только необратимое удаление (есть защита
  «нельзя удалить последнего» — это хорошо, но альтернативы «временно
  отключить» нет).
- ~~**Нет журнала действий**~~ — **закрыто.** Общий журнал изменений по
  всему сайту (не только по одному острову) — см. раздел «Общий журнал
  действий — сделано» ниже.
- **Нет «последний вход»** в списке пользователей — только дата создания
  аккаунта, не активность.

**Первый практический шаг — сделано:** `PATCH /api/auth/users/:id` — смена
роли существующего пользователя (без удаления/пересоздания аккаунта) +
принудительный сброс пароля (`must_change_password=1`, тем же путём, что и
обычное приглашение — пользователь просто вынужден задать новый пароль при
следующем входе, доступ не блокируется немедленно). Защита «нельзя понизить
последнего администратора» — та же, что уже была на удаление. Если админ
меняет роль самому себе — применяется сразу к текущей сессии, без
перелогина. В панели настроек: статичный бейдж роли заменён на выпадающий
список (с confirm на смену), добавлена кнопка «Сбросить пароль» и бейдж
«ожидает смены пароля» у тех, кому она предстоит. 10 бэкенд-тестов, 3
e2e-теста (живьём не прогонялись, как обычно).

**Не сделано:** скоупинг прав по проекту (роль редактора сейчас глобальная
на все проекты сразу) — отдельная, более крупная задача, не в этот заход.
Журнал действий и «последний вход» — тоже не в этот заход, завязаны на
будущую историю правок.

## Живое тестирование (первый реальный прогон) — найдено и разобрано

Первый живой прогон бэкенд-тестов и e2e на Windows после всей сессии
(до этого — только синтаксическая проверка и Linux-песочница). Два
инфраструктурных бага нашлись и починены сразу:

- **`test/backup-full.test.js` падал на Windows с `EPERM`** при уборке
  временной папки — не баг продукта (`restore-full` к этому моменту уже
  отработал и проверен), просто этот единственный файл пересоздаёт
  соединение с БД несколько раз подряд (`freshApp()` на каждый restore), и
  native-биндинг `node:sqlite` иногда не успевает отпустить файловый лок
  на Windows даже за 5×200мс повторов, которых достаточно везде в
  остальных тестах с одним соединением. Увеличил ретраи и обернул
  уборку в try/catch с предупреждением вместо падения — это не проверка
  корректности, а простая уборка мусора.
- **`e2e/global-setup.js` падал с 401** при попытке зарегистрировать
  тестового редактора — рассчитывал на совсем пустую базу (bootstrap-
  регистрация без входа), но сервер сам сажает в пустую базу дефолтный
  `admin`/`admin0000` при первом старте (см. `db.js`), так что база к
  этому моменту уже не пуста. Поправил — логинимся дефолтным админом,
  регистрируем тестового редактора уже от его имени.

## Живой фидбек по использованию (docx, ~24 пункта) — большой батч, разбор по приоритету

Получен документ с конкретными наблюдениями после реального использования
сайта — гораздо ценнее любого статического аудита, потому что вскрывает
то, что невозможно найти чтением кода. Разобрано на три уровня.

### 🔴 Критичные баги — разобрано 5 из 7

Найдены и починены (все — фронтенд, бэкенд не тронут, 229/229):

1. ~~**Клик по неразмещённому острову в лотке сам ставит его на карту**~~ —
   **починено.** `startPointerDrag()` вычисляет флаг `moved` (было ли
   реальное перетаскивание, не просто клик) и передаёт его 4-м параметром
   в `onEnd` — но оба места, где паттерн использовался (лоток
   неразмещённых островов в `mapView.js` и лоток неразмещённых локаций в
   `detailView.js`), принимали только `(x, y)`, полностью игнорируя флаг.
   Поскольку оба лотка визуально лежат поверх карты, обычный клик без
   перетаскивания всё равно проходил проверку границ и ставил
   остров/локацию ровно в точку клика. Добавлена проверка `if(!moved)
   return;` в обоих местах.
2. ~~**Многоугольник «рисует бесконечные линии, не соединяет, только
   сброс»**~~ — **не баг, отсутствие подсказки в моменте.** Логика на
   самом деле корректна: клик добавляет точку, двойной клик или Enter
   завершает фигуру, Esc отменяет — но это было написано только в `title`
   кнопки инструмента, который почти никто не наводит мышью. Добавлен
   `toast()`-хинт при выборе инструмента «Многоугольник»/«От руки» с
   явным описанием, чем закончить (`toast()` научен принимать свою
   длительность показа третьим параметром — дефолтных 1.6с не хватало
   на прочтение инструкции).
3. ~~**Написанный текст-аннотацию нельзя подвинуть**~~ — **починено,
   реальный баг.** Перетаскивание уже существующей фигуры разрешалось
   только при **выключенном** инструменте рисования (`if(!state.editorOn
   || state.drawTool) return;`) — но инструмент «Текст» намеренно остаётся
   выбранным после создания подписи (чтобы можно было писать следующую
   подряд), поэтому клик по только что написанному тексту молча ничего не
   делал. Условие ослаблено до `state.drawTool==='erase'` — двигать можно
   при любом активном инструменте, кроме ластика (у него свой смысл клика).
   Побочный эффект (сознательный, не баг): клик ровно поверх существующей
   фигуры любым инструментом теперь двигает её, а не рисует новую фигуру
   под ней — так ведёт себя большинство графических редакторов.
4. ~~**Острова сами двигаются в режиме рисования**~~ — **починено,
   реальный баг.** `makeMarkerDraggable()` вообще не проверял
   `state.drawTool` — маркер острова перетаскивался по `mousedown`
   независимо от того, выбран ли инструмент рисования. Добавлена проверка
   `if(state.drawTool) return;` в начале `mousedown`/`touchstart`.
5. ~~**Событие мировой хронологии всегда уходило в проект «Аллоды
   Онлайн»**~~ — **починено**, нашлось рядом при разборе пункта про
   ошибку «499» (сам код ошибки не воспроизведён). `state.project` не
   передавался в теле запроса `createEventFlow` для `scope:'world'` —
   бэкенд в этом случае молча подставлял дефолтный проект, независимо от
   того, какая вкладка открыта. Добавлена передача `body.project =
   state.project`.

**Не разобрано — нужны детали, чтобы не гадать вслепую:**

6. **Ошибка «499» при добавлении события хронологии.** 499 — не код,
   который этот сервер в принципе отдаёт (ни rate-limiter, ни `/timeline`
   его нигде не шлют). Похоже на опечатку (400/500) или на что-то сетевого
   уровня. Нужно: точный текст ошибки/статус из вкладки Network в devtools.
7. **«В какой-то момент сбросились все размещённые острова».** Самое
   тревожное из всего списка. Проверены все `UPDATE` на `allods` в
   бэкенде — ни один не может массово задеть `mapX`/`mapY` (везде чёткий
   `WHERE id=`), проверены все глобальные `keydown`-обработчики — ничего
   похожего на случайный триггер сброса. Нужно: что делалось непосредственно
   перед этим — переключение проекта? импорт/восстановление БД? обновление
   страницы во время чего-то?
8. **«Нажал на текстовое поле, его сьело текст».** Не удалось определить,
   какое именно поле — описание/история острова (contenteditable,
   логика сохранения по blur выглядит корректной при чтении кода), текст
   аннотации на карте (`prompt()`, надёжный нативный диалог, сложно
   потерять текст) или что-то из тег-редакторов (`editTagField` и
   подобные). Нужно: какое именно поле, что вводилось, что произошло
   после клика.

### 🟡 Уже было в UX-аудите — теперь подтверждено живым использованием

Ничего нового не открыто, но конкретные формулировки из фидбека прямо

- «Можно все такие окна сделать в стиле сайта? Выбивается из стиля» —

## Аудит безопасности — исправлено

- Инструменты рисования (круг/квадрат/линия) почти не кликались для
  удаления — `pointer-events:auto` на фигурах без заливки (`fill="none"`)
  резолвился в `visiblePainted`. Поставлено `pointer-events:all`.
- Редактирования уже размещённых фигур не было вообще — бэкенд
  (`PATCH /annotations/:id`) был готов и покрыт тестами, но фронтенд его не
  вызывал. Добавлено перетаскивание мышью с сохранением через тот же `PATCH`.
- Асинхронный `crypto.scrypt` вместо `scryptSync` (см. пункт 7 выше).
- Внешние ссылки на иконку/картинку галереи/карту локации были нерабочими:
  CSP `img-src` не разрешал внешние хосты. Добавлено `https:` в `img-src`.
- Async-роуты (`register`/`login`/`password`/`check-updates`) не были
  обёрнуты в try/catch — необработанный reject валит процесс на Express 4.
  Обёрнуты, ошибки уходят в общий error-handler.
- Мелкий XSS в рендере результатов «Проверить обновления» (версии пакетов
  из npm registry вставлялись в `innerHTML` без экранирования) — добавлен
  `escapeHtml()`.
- `dompurify` 3.4.12 → 3.4.13 — `npm audit` нашёл умеренную XSS-уязвимость
  (GHSA-55q2-fjhq-7xh7). Наш код не использует уязвимый режим (`IN_PLACE`),
  но обновлено в любом случае — `npm audit` теперь чистый.
- **Session fixation при логине.** `req.session.regenerate()` не вызывался.
  Добавлено пересоздание ID сессии в `login` и в bootstrap-ветке `register`.
- **`GET /api/system` и `/api/system/check-updates` были доступны без
  логина** — версия Node, PID, память процесса и версии зависимостей были
  видны любому посетителю. **Закрыто ролевой моделью** (см. ниже) —
  теперь требуют роль `admin`.

## Ролевая модель — сделано

Раньше было бинарно (залогинен = полный доступ). Теперь три уровня:

- **Гость (не залогинен)** — только просмотр, как и было.
- **Редактор (`editor`)** — полный доступ к контенту: острова, локации,
  галерея, аннотации на карте, фракции, украшения. Не видит панель
  «Настройки» и «О системе», не может управлять пользователями/бэкапами/
  импортом (это деструктивные или административные операции).
- **Администратор (`admin`)** — всё вышеперечисленное плюс настройки сайта,
  логотип, бэкапы (скачать/восстановить), импорт (полная замена БД),
  управление пользователями, «О системе» + проверка обновлений.

Первый аккаунт на сервере всегда становится `admin` — и при первой
регистрации с нуля, и при миграции со старых схем (протестировано оба
сценария: самая старая одноаккаунтная `auth`-таблица и промежуточная
многопользовательская без ролей — везде существующие аккаунты становятся
`admin`, не понижаются молча до `editor`). Новых пользователей может
приглашать только `admin`, по умолчанию с ролью `editor`, если явно не
указано иначе. Нельзя удалить последнего пользователя вообще и нельзя
удалить последнего `admin`. `doc/index.html` обновлена под новую модель.

**Открытый пункт, не реализовано:** форма «предложить правку» для
незалогиненных гостей (с алертом на почту и/или отдельной панелью для
редактора/админа на модерацию). Нужна инфраструктура отправки писем
(SMTP-настройки), которой в проекте пока нет — либо ограничиться только
внутренней панелью-очередью без email. Ждёт решения, что именно нужно.

## Дефолтный аккаунт admin/admin0000 — сделано

Защита от дурака: на свежей БД без единого пользователя сервер сам создаёт
`admin`/`admin0000` при старте (`db.js`), вместо открытого bootstrap-экрана
«создайте первый аккаунт». Обязательная смена пароля при первом входе
(`must_change_password` в БД + сессии) — непропускаемая форма поверх всего
интерфейса, без кнопки «отмена». Распространяется и на любой аккаунт,
который завёл администратор для кого-то другого (начальный пароль выбирал
не сам пользователь) — только не на bootstrap/самостоятельно выбранный
пароль, там форсировать нечего.

**Проверено (в т.ч. специально по твоему вопросу «что будет, если удалить
admin»):**
- Дефолтный admin нельзя удалить, пока это последний оставшийся аккаунт
  (400, понятная ошибка).
- Если есть другой admin — дефолтный удаляется свободно, сайт не осиротевает.
- `npm run reset-password` → удалить все аккаунты → на следующем запуске
  сервера `admin`/`admin0000` пересевается заново автоматически. По пути
  нашёл и поправил баг — сам скрипт показывал устаревшее сообщение про
  несуществующий уже bootstrap-экран.

Отдельный файл тестов `test/default-admin.test.js` целиком про это. Заодно
пришлось переписать бутстрап-сценарии примерно в 8 других тестовых файлах —
раньше они полагались на «первый пользователь появляется через открытую
регистрацию», а теперь на свежей БД пользователь есть с самого начала.

**Осознанно не сделано:** принуждение к смене пароля только на фронтенде —
бэкенд не блокирует остальные роуты, пока флаг не снят. Это соответствует
формулировке задачи («для защиты от дурака», не от обхода через devtools) —
если нужно жёстче (мидлварь, блокирующая мутации до смены пароля), это
отдельная, более инвазивная доработка.

`VERSION` напрямую в рантайме, синхронизировать их не нужно.

## Аудит функционала — чего не хватает для полноценной вики

_Перепроверено после сессии с Источниками/Хронологией/Архипелагами/HTTPS —
ни один из пунктов ниже эта сессия не закрывала, список ниже всё ещё
актуален полностью._ Основные пробелы относительно стандартного вики-движка
(MediaWiki и подобные), по убыванию важности:

1. ~~**Истории правок нет вообще.**~~ — **закрыто.** Простые снимки
   (`allod_snapshots`) на каждый PATCH, см. предложение №3 выше в «Сделать
   в первую очередь». Diff и откат — всё ещё нет, только просмотр снимка
   целиком (осознанно, см. там же). **Не путать с «Хронологией»** (сделана
   раньше в этой же сессии) — та про историю *внутри выдуманного мира*
   (когда остров появился/погиб и т.п.), а не про историю правок самой
   вики-статьи — это разные вещи, обе теперь сделаны.
2. ~~**Поиск ищет только по названию острова**~~ — **закрыто.** Полнотекстовый
   FTS5-поиск по `description`/`history`/`plot` сделан, см. предложение №2
   выше в «Сделать в первую очередь». Мгновенный клиентский фильтр по
   названию (для меток на карте) остался как отдельный, более быстрый слой —
   не заменён, а дополнен.
3. **Текст статей — обычный plain text**, не вики-разметка: нет
   заголовков/списков/жирного текста, и главное — нет кликабельных
   вики-ссылок между статьями (`[[Остров]]`).
4. ~~Права доступа бинарные~~ — **закрыто ролевой моделью** (см. выше).
   Остаётся: нет защиты отдельных страниц от правок конкретных редакторов.
5. **Категории — просто фильтр**, не отдельные страницы-разделы со
   списком всех статей категории.
6. Нет обсуждений/комментариев к статьям.
7. Нет редиректов при переименовании острова, нет «what links here», нет
   ленты последних изменений, нет печати/экспорта отдельной статьи.

## Разделение кода и данных (после этапа наполнения)

Пока идёт работа над юзабилити — 318 сид-островов из `seed-data.json`
крутятся как есть, это нормально и ожидаемо. Когда начнётся реальное
наполнение сайта контентом, нужно чётко развести две вещи, которые сейчас
живут рядом, но должны стать независимыми:

- **Код и статика сайта** — версионируется, обновляется через git/образ,
  ничего пользовательского внутри не хранит.
- **Данные** — база (`atlas.db`), загруженные файлы (`uploads/`) и бэкапы
  (`backups/`) — не версия кода, а состояние конкретного сайта.

**Что уже готово архитектурно** (проверено в `docker-compose.yml`):
именно так уже разведено — `ATLAS_DB_PATH`/`ATLAS_UPLOAD_DIR`/
`ATLAS_BACKUPS_DIR` смотрят в именованные Docker-тома (`atlas-db`,
`atlas-uploads`, `atlas-backups`), а не внутрь образа. Пересборка образа
(`docker compose up --build`) их не трогает — то есть база формально
переживает обновление кода уже сейчас.

**Сделано:** единый архив «данные сайта» = БД + uploads одним `.zip`
(`GET /api/backup/download-full` / `POST /api/backup/restore-full`,
UI — «⚙ Настройки» → «📦 Полный архив сайта»). Раньше `restore` тащил
только `.db`, ссылки на картинки после переезда указывали в никуда — теперь

## Найдено попутно: старт-скрипты и порты — разобрано

**Порты (полная карта):**
- Локальный запуск (`node server.js`, `start.bat`, `start.sh`,
  `docker-compose.local.yml`) — один порт, `4173`, обычный HTTP.
- Прод (`docker-compose.yml` + Caddy) — наружу `80` и `443` (Caddy,
  автовыпуск Let's Encrypt); сам `app`-сервис порт наружу вообще не
  пробрасывает (`ports:` есть только у `caddy`) — недоступен напрямую с
  хоста, только через Caddy по внутренней docker-сети.

**Баг: браузер открывался раньше, чем сервер реально готов.**
`start.bat` строкой ДО `node server.js` вызывал `start "" "url"` — открывал
вкладку сразу, без всякой проверки готовности. `start.sh` был мягче, но
тоже гадал — фиксированный `sleep 1.5` перед попыткой открыть браузер,
которого на медленной машине или при первом запуске (засев 318 островов в
БД) может не хватить. Правильный (единственно надёжный) момент — колбэк
`app.listen()`, он срабатывает ровно тогда, когда сервер начал принимать
соединения. Теперь браузер открывает сам `server.js` изнутри этого
колбэка, по флагу `ATLAS_OPEN_BROWSER=1`, который выставляют оба стартовых
скрипта — сам по себе `node server.js` (например, при запуске из терминала
руками) браузер не трогает. Проверено живьём — сервер переживает и
успешное, и неуспешное (нет GUI-браузера) открытие, не падает в обоих
случаях.

**«Нужно два раза запускать start.bat».** Не нашёл в самом скрипте
реального бага, который бы это объяснял — свежий `npm install` в этом
проекте отрабатывает чисто, с кодом выхода 0, никаких обманчивых
сообщений об ошибке. Наиболее вероятное объяснение: `npm install` в
первый раз действительно не мгновенный (зависимость `sharp` тянет
платформенный нативный бинарник) и не показывает никакого прогресс-бара —
окно может выглядеть «зависшим», и если его закрыть руками, второй запуск
уже увидит `node_modules` на месте и сразу перейдёт к старту сервера,
создавая ощущение «первый раз только ставит, второй — реально работает».
Смягчил — оба скрипта теперь явно предупреждают «это может занять минуту-
другую, не закрывайте окно» перед `npm install`. Если проблема
воспроизведётся снова после этого — значит, дело не в перцепции, а в чём-то
другом, и стоит прислать точный вывод консоли в момент, когда окно
закрывается.

## Найдено попутно: полный проход по всем 10 скриптов запуска/установки/тестов

По просьбе — прошёлся по каждому из `install.bat/.sh`, `start.bat/.sh`,
`test.bat/.sh`, `test-backend.bat/.sh`, `test-e2e.bat/.sh` (с явным учётом,
что рабочая локаль — русская):

- **`setlocal` добавлен во все `.bat`-файлы.** Без него переменные вроде
  `set ATLAS_OPEN_BROWSER=1` меняют окружение всей сессии cmd.exe, а не
  только текущего скрипта — незаметно при обычном двойном клике (новый
  cmd.exe и так закрывается целиком), но протекает наружу, если скрипт
  когда-нибудь вызовут через `call` из другого `.bat`. Защитная мера на
  будущее, не действующий сейчас баг.
- **`chcp 65001 >nul` → `chcp 65001 >nul 2>&1`** везде — глушим и стандартный
  вывод, и поток ошибок переключения кодовой страницы, чтобы случайный сбой
  этой команды не плевался мусором в консоль до того, как скрипт вообще
  начал что-то делать. Не нашёл более глубокой проблемы с русской локалью
  специально — `chcp 65001` в начале файла (до первого `echo` с кириллицей)
  и сохранение файлов в UTF-8 с CRLF — это ровно правильный, стандартный
  рецепт для отображения кириллицы в cmd.exe на современной Windows
  (10/11); более старые версии Windows (до обновления 1903, 2019 года) имели
  собственные баги парсинга UTF-8-батников даже при верном `chcp`, но это
  ограничение самой ОС, не то, что можно починить на стороне скрипта.
- **Разошедшиеся по файлам предупреждения о времени установки.** В прошлый
  раз «это может занять минуту-другую, не закрывайте окно» получили только
  `start.bat`/`start.sh` — привёл к тому же виду `install.bat/.sh`,
  `test.bat/.sh`, `test-backend.bat/.sh`.
- **Скачивание браузеров Playwright для e2e — отдельная, гораздо более
  долгая загрузка** (Chromium + WebKit, сотни мегабайт), которую раньше не
  отличали от обычной установки npm-пакетов одним общим «может занять пару
  минут». Теперь у неё своё отдельное явное предупреждение в
  `test.bat/.sh` и `test-e2e.bat/.sh`.
- **`test.bat`/`test-e2e.bat` не проверяли код выхода `install-browsers`.**
  Если скачивание браузеров падало (например, из-за сети), скрипт раньше
  всё равно тихо продолжал к `npm test`, и тесты падали с гораздо менее
  понятной ошибкой «браузer не найден» вместо явного «установка браузеров
  не удалась». Добавил `if errorlevel 1` сразу после, как у остальных шагов.

**Проверено вживую** (насколько возможно без реальной Windows-машины в
песочнице): `test-backend.sh` — полный прогон, 156/156; `install.sh` —
дважды (чистая и повторная установка), сообщения появляются корректно;
`test.sh` — бэкенд-часть проходит, e2e закономерно падает на отсутствии
GUI-браузера в песочнице (не связано со скриптом). Баланс скобок во всех
`.bat`-файлах и CRLF-концы строк проверены статически — вживую на Windows
не гонял, у меня её тут просто нет.

### Слайдер динамики островов — сделано

Год + чекбокс «Показать все острова» — фильтрует видимость меток на карте
по `year_appeared`/`year_disappeared` (эти поля уже были заведены раньше
для статуса «уничтожен»). Полностью клиентская фича — фильтр в
`passesFilter()`/`islandExistsAtTimelineYear()` (state.js), считает
остров существующим на выбранный год если `year_appeared <= год <
year_disappeared` (обе границы `null` трактуются как «всегда» с
соответствующей стороны). По умолчанию чекбокс включён (фильтр по году
выключен — текущее поведение «показывать всё» не меняется, пока человек
явно не тронет слайдер).

Диапазон слайдера считается на клиенте из уже загруженных данных (минимум/
максимум среди всех `year_appeared`/`year_disappeared` текущего проекта);
если ни у одного острова эти поля не заполнены — панель слайдера не
показывается вообще, а не висит бессмысленным пустым виджетом. При смене
проекта год сбрасывается — то, что имело смысл для одного проекта, не
обязательно осмысленно для другого.

Статус «уничтожен» на маркерах (см. раздел «Подсветка фракции + статус
"уничтожен"» выше) теперь учитывает текущее положение слайдера — как и
планировалось там: в режиме «показать все» логика осталась плоской (год
задан — значит уничтожен, независимо от какого года), но когда слайдер
активен — маркер помечается уничтоженным только если `year_disappeared`
уже наступил относительно выбранного года слайдера (остров, которому ещё
предстоит погибнуть в будущем, на более раннем годе показывается живым).

Точка входа — панель внизу карты (тот же паттерн позиционирования, что и у
`#zoomCtrl`, только по центру), видна на самой карте любому посетителю, не
только редактору — это про чтение мира, не про его редактирование.
Панель выделения архипелага (тоже внизу по центру, из прошлого захода)
поднята выше через `body:has(#timelineSliderBar.show)`, чтобы не
перекрывались, если обе видны одновременно.

написан — включая проверку, что маркер пропадает/появляется на границах
года появления/исчезновения и что чекбокс «показать все» отменяет фильтр,
живьём не прогонялся.

## HTTPS — сделано, единый механизм на все способы запуска

Раньше HTTPS был только в Docker-режиме через Caddy (порты 9311/9312,
самоподписанный локально или Let's Encrypt для публикации), а `start.sh`/
`start.bat`/голый `node server.js` — без HTTPS вообще, порт 4173. Теперь
везде — **один и тот же нативный механизм**, Caddy убран полностью:

- **`server/certs.js`** — разрешение сертификата: сначала внешний готовый
  (`ATLAS_CERT_FILE`/`ATLAS_KEY_FILE` — для публикации, выпускает и
  продлевает certbot снаружи, сервер только читает PEM), иначе локальный
  самоподписанный — каскад `openssl` (если есть в PATH) → npm-пакет
  `selfsigned` → голый HTTP, если совсем ничего не вышло (не падает).
  Самоподписанный кэшируется на диске между рестартами, чтобы браузер не
  просил заново подтверждать исключение. Нормализация `\r\n` в PEM — важно
  на Windows.
- **`start.sh`/`start.bat`** — теперь тоже HTTPS на 9311 (редирект с 9312),
  самоподписанный, без Docker вообще.
- **`docker-compose.local.yml`** — Caddy убран, тот же нативный механизм
  прямо в контейнере приложения, сертификат в отдельном именованном томе.
- **`docker-compose.yml`** (публикация) — тоже без Caddy: порты 80/443
  снаружи мапятся на непривилегированные 9312/9311 внутри контейнера
  (процесс не root), сертификат — готовые файлы от внешнего certbot
  (пошаговая инструкция в README: webroot-валидация через собственный
  редирект-сервер приложения, копирование в `./certs`, `docker compose
  restart app`, cron на продление).

**Проверено живьём:** оба режима `server.js` (native HTTPS и обычный HTTP)
реально поднимаются, HTTPS отвечает на `/api/health`, редирект-сервер верно
301-ит на HTTPS. Сертификат сгенерировался через `openssl`-путь каскада (он
доступен в этом окружении). 5 новых тестов на `certs.js` (внешний
сертификат имеет приоритет, кэширование самоподписанного, нормализация
PEM, откат при битом/отсутствующем внешнем сертификате).

**Не проверено:** сама Docker-сборка (`docker compose up --build`) —
Docker недоступен в песочнице, только синтаксис YAML. certbot-флоу для
реальной публикации описан в README, но ни разу не прогонялся на настоящем
домене. Windows-путь (`start.bat` + генерация сертификата) не проверялся
вживую — нет Windows-машины под рукой.

## Архипелаги — контейнер вместо тега, сделано целиком (бэкенд + фронтенд)

Обсуждали отдельно: архипелаг должен быть настоящим контейнером (острова
принадлежат ему через FK), а не текстовым полем-тегом, с групповым
управлением (ctrl+клик на карте) при сохранении перехода на каждый остров
по отдельности.

**Бэкенд:**
- `archipelagos` (id, project, name) + `allods.archipelago_id` (FK,
  `ON DELETE SET NULL` — удаление архипелага не удаляет острова, только
  открепляет, как договорились).
- Авто-миграция старых текстовых значений `allods.archipelago` в записи
  при первом запуске на существующей базе — группировка по (project,
  текст), проверено тестом на специально "состаренной" базе (два проекта с
  одинаковым текстом не схлопнулись в одну запись).
- `POST /api/archipelagos/assign` — массовая привязка нескольких островов
  сразу (под ctrl+клик), создаёт новый архипелаг или использует
  существующий по id. `unassign` — открепить один остров.
- 12 тестов (CRUD + bulk-assign + миграция) — все зелёные.

**Фронтенд — три точки входа, как договаривались:**
- Ctrl/cmd+клик по маркерам на карте (только в редакторе) — плавающая
  панель «Собрать в архипелаг» снизу карты, с номерным выбором
  существующего архипелага или вводом нового названия. Отдельная кнопка
  «✕» в панели снимает выделение без создания.
- Кнопка «+🏝» у каждой строки острова в Атласе островов (без ctrl+клика —
  как и решили, там это отдельная точечная операция, не групповая).
- Глобальная страница «🏝 Архипелаги» — список, состав каждого (с
  переходом на каждый остров по отдельности), переименование/удаление для
  редактора.
- Пикер на странице острова (выпадающий список — как переключатель
  проекта) взамен старого текстового тега. Для гостя (не редактора) —
  просто текстовое отображение названия архипелага, если он привязан.
  Старое поле `allods.archipelago` физически осталось в схеме
  (миграционный источник), но фронтенд им больше нигде не пользуется —
  старая строка в сайдбаре убрана.

Синтаксически проверено, бэкенд не пострадал (199/199). e2e-тесты на весь
флоу (кнопка в Атласе, ctrl+клик + панель, снятие выделения, пикер на
странице острова, удаление архипелага не трогает острова) написаны, живьём
не прогонялись — нет браузеров Playwright в песочнице.
